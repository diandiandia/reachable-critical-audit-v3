## 2. 可修改性评估：v2.2 修改方案能解决多少？

### ✅ 可通过工程修改解决（约 18 类，C 层全部 + B 层一半 + A 层小半）

**C 层 12 类全部可改**（纯工程，明确无歧义）：
- C1-C10: 参数解析、merge 语义、校验一致性、门禁规则、batch 参数、R4 stages、JSON 容错、字段填充、依赖清单、状态码——每项都是确定性代码修复，有明确验收标准
- C11-C12: 指标公式修正 + (file,line) 跨 CWE 关联标注

**B 层可改 5 类**：
- B1 部分可改：**机械降噪层**（F1 vendored 清单 + F2 非-sink 集合 + F3 硬编码参数判定）是确定性过滤，WordPress 审计已证明三层过滤能砍 99.6% 候选且可问责——内建为 `triage.py` 即可
- B4 可改：R4 规模自适应档位（小项目 3×2 / 大项目 6 / 战役 1×6 + r4_consolidated 标注）
- B6 可改：pending 心跳 + 落盘冲突检测 + schema 强制 + 中断恢复指引
- B7 可改：簇级验证官方化（cluster_id + 簇级 collect/assert + verdict_map 语义）
- B8 可改：R0.5 `--cross-tags` 模式 + grep 词表分级

**A 层可改 3 类**：
- A5 可改：锚点注册表扩展（10 语言战役已补 9 语言，机制运行良好）
- A7 可改：语言→测试路径形态映射表（战役已产出 5 条）
- A2 部分可改：framework_scope 字段 + 不匹配框架时 regex 命中降级（机械可判）

**v2.2 路线图结论**：~18 类（58%）是明确的工程修复，工作量为中等（工具链改动 + 规则数据标注），**应当做**——它们解决的是"正确性"（C3 断言不一致 4 次复现）与"效率"（B1 降噪 100 倍）问题。

### ⚠️ 修改只能缓解、不能根治（约 7 类）

| # | 问题 | 修改方案 | 修改的极限 |
|---|---|---|---|
| A1 | L0 规则语义缺失 | 逐语言语义化改造（C/Java/PHP 各写语义排除层） | **每修一个生态，下一个生态又全盲**——10 语言战役证明 15 语言 × 无限框架 = 组合爆炸；规则库作为"产品"永远滞后于目标 |
| A3 | 源模型不匹配 | 平台 profile 化（RPC/服务端/嵌入式） | profile 数量 = 生态数量，同上矛盾 |
| B2 | verifier 幻觉 | 任务书强制"调用边 grep 证据" | 只能降概率不能消除——LLM 性质决定；需实证兜底（B5） |
| B3 | 判定缺前提维度 | 任务书加 platform_precondition/受信边界准则 | 前提维度是开放集合（平台/受信/配置/部署…），枚举不完 |
| B5 | 无实证抽验 | 新增 R5 阶段 | R5 本身可行（本次已证明），但它的存在承认了静态判定的不可信——是补丁不是根治 |
| B10 | 成熟项目全噪音 | 成熟度评估前置 | 缓解，但成熟度是连续谱且需人工判断 |

### ❌ 修改救不了（约 3 类，架构级根因）

1. **A4 规则库-输入面匹配的根本矛盾**：11 次审计的全部真实发现（33+ 家族）**无一来自 L0 规则**（CWE-89 SQL 拼接靠 L1、ssi.exec 靠 R4、ws 帧缓冲靠人工家族复用、display_name XSS 靠人工比对）。这不是"规则写少了"——是"规则命中=候选"的**产品形态**错了：静态签名库对现代框架的 sink 生态（协议编解码、异步缓冲、框架 wrapper）结构性不可见。修 A1/A3 只是把盲区从 95% 降到 90%。
2. **B2/B5 组合的验证信任问题**：LLM verifier 的 REACHABLE 判定需要独立证据源。工具链修改给不了证据源，只有架构上的"证据多样性"（静态链 + 调用边证明 + 实证 harness + 上游 diff）能给。
3. **指标体系建立在错误假设上**（A4 的镜像）：SDR/SNR/coverage 全部假设"规则库是完备基线"。规则库不可能是完备基线时，指标衡量的是幻觉。C11 的公式修补改变不了哲学。

## 3. 新架构评估（v3 方向）

### 证据支持的核心判断

> 11 次审计的数据：**L0 规则命中 155,000+ 条，直接产出 REACHABLE 0 条；全部 40+ 个真实发现来自 L1（框架感知）、R4（业务假说）、R0.5（考古）与主 Agent 人工比对。** 当前架构中，规则库是"最贵的噪音源"，LLM 子智能体是"唯一的分析引擎"，而流程设计把 LLM 当"验证器"用、把规则库当"主引擎"用——角色与能力完全颠倒。

### 候选方案

#### 方案 1：攻击面测绘先行（Threat-Model-First）——推荐核心
- **阶段 0 改为输入面测绘**：LLM agent 枚举项目的真实输入面（网络端点/协议解码/IPC/文件上传/配置通道/环境注入），产出 `input_surface.json`（本次战役中 extractor 的"项目背景注入"已被证明是 L1 产出的决定性因素——把它前置为正式阶段）
- **规则扫描降级为辅助信号**：只对测绘出的输入面做局部规则匹配（签名库从"全库轰炸"变为"面内提示"），候选量从 5 万级降到百级
- **证据**：Dubbo 的真实输入面（Netty/registry/泛化调用）全部靠 L1 兜住；lighttpd 的 buffer/protocol/spawn 生态全部靠主 Agent 背景注入；Vapor 的 25 条 L1 全靠三域手工增强——**输入面测绘是三者的统一抽象**

#### 方案 2：签名库替代规则库（Signature Hint Library）
- 签名按**语义**表达（危险操作语义 + 边界条件），语言无关，数量级从"15 语言 × N 框架 × M 方法名"压缩到"语义族 × 平台 profile"
- 签名的作用是"提示 LLM 该看什么"，不是"判定"——判定权归证据链
- 融合 A6 LOGIC_PATTERN 的经验：语义缺陷（白名单弱化、修复-再暴露）比 sink 更接近真实 CVE

#### 方案 3：实证验证一等公民（Evidence-Graded Verdicts）
- REACHABLE 分级：`static_only`（仅静态链）< `edge_proven`（每跳有 grep 证据）< `empirically_confirmed`（harness 实测）
- DoS/崩溃/内存类声称强制实证（vapor/ktor/actix/AWStats 四次实测证明 harness 成本低、置信度极高、且抓出过幻觉）
- 修正闭环：实证证伪 → 回溯修正 verifier 错误并记录（H3-L1 模式制度化）

#### 方案 4：指标重构（过程问责制）
- 核心指标：输入面覆盖率、验证深度分布、实证验证率、verdict 修正记录
- SDR/SNR 降为参考指标；新增"L0 噪音率自检"（>80% 自动禁用规则并提示）

### 推荐架构：v3 = 测绘驱动 + 证据分级 + 签名提示

```
R0  工具自检（锚点召回保留，扩展为"签名库冒烟"）
R0.5 考古（保留 + --cross-tags）
R1  输入面测绘（LLM 主导，产出 input_surface.json）   ← 新主引擎
R2  签名提示 + 面内规则匹配（候选百级，不再全库轰炸）   ← 规则库降级
R3  双向回溯 + 调用边证据强制（每跳 grep 证据）
R4  业务假说 + 信任边界专项（gvisor/container 教训）
R5  实证抽验（DoS/崩溃类强制，verdict 分级）
报告  过程问责指标
```

**角色重排**：LLM 从"验证器"升级为"主分析引擎"（测绘+回溯+判断），规则库从"主引擎"降为"提示库"（签名），工具链从"编排队列"升级为"证据账本"（每个 verdict 附证据类型与来源）。

### 迁移成本评估

- v2.2（修改方案）：~18 类工程修复，1-2 周工作量，**立即做**——解决正确性与效率问题，为 v3 打底
- v3（架构转型）：R1 替换 + verdict 分级 + 指标重构，2-4 周，**应基于 v2.2 后的下一轮审计数据决策**——方案 1/3 的假设（输入面测绘产出质量、实证分级成本）已被本次战役的 extractor/实测实践预验证，风险可控

### 风险与反方论点

1. **签名库会不会重蹈规则库覆辙**：签名仍可能盲区——但签名是"提示"而非"判定"，盲区代价从"漏报"降为"该面没被提示"，且输入面测绘不依赖签名完备性
2. **输入面测绘的质量依赖 LLM**：11 次审计证明 LLM 的测绘能力（extractor 产出 100% 真实发现）强于其验证能力（H3-L1 幻觉）——把 LLM 放到它擅长的位置是顺势而为
3. **实证成本**：DoS/崩溃类 harness 成本低（本次 4 个 harness 各 <1h），但逻辑类漏洞（鉴权绕过）难以实证——需保留证据分级，不强制所有类型
